| Код | Требования | Комментарий |
|-----|------------|-------------|
| F | Функциональные (Functionality) | |
| F1 | Подача заявки на депозит/кредит через сайт (для новых клиентов) с ФИО и телефоном. | Требует интеграции с системой кол-центра и АБС. |
| F2 | Подача заявки на депозит/кредит через интернет-банк (для существующих клиентов) с выбором счёта, суммы и подтверждением по СМС. | Интеграция с ядром для СМС-подтверждения. |
| F3 | Отображение актуальных ставок по депозитам и кредитам на сайте и в интернет-банке. | Ставки хранятся в XLS → требуется централизованное хранилище (например, в АБС или отдельном сервисе). |
| F4 | Персонализированные ставки и предодобренные предложения в интернет-банке. | Требует интеграции с Кредитным конвейером и скорингом. |
| F5 | Автоматическая проверка скоринга при заполнении паспортных данных на сайте (для новых клиентов). | Интеграция с системой скоринга и бюро КИ. |
| F6 | Единая заявка: если клиент подал заявку на сайте, менеджер в отделении должен продолжить работу с ней в АБС. | Требует сквозной идентификатор заявки и синхронизацию между системами. |
| F7 | Уведомления по СМС о статусах заявки (подтверждение ставки, открытие депозита, одобрение кредита и др.). | Интеграция с сервисом уведомлений (через ядро или отдельный модуль). |
| U | Удобство использования (Usability) | |
| U1 | Интерфейс должен соответствовать корпоративной системе дизайна (цвета, элементы, брендирование). | Важно для UX, но не влияет на архитектуру напрямую. |
| U2 | Быстрый отклик интерфейса: время загрузки справочных данных ≤ 200 мс. | Требует кэширования, оптимизации запросов, возможно — вынос справочников в отдельный сервис. |
| R | Надёжность (Reliability) | |
| R1 | Доступность сервисов 99,9% (24/7). | Архитектурно значимо: требует отказоустойчивости, резервирования, распределения нагрузки. |
| R2 | Защита персональных данных при передаче (шифрование трафика — TLS 1.2+). | Обязательное требование безопасности и регуляторики. |
| R3 | Резервный ЦОД с возможностью переключения при сбое основного. | Требует архитектурного решения по геораспределённости и синхронизации. |
| R4 | Изоляция интернет-банка от прямых вызовов АБС (из-за нагрузки и надёжности). | Критично: необходимо ввести промежуточный слой (API Gateway, очереди, буферные сервисы). |
| P | Производительность (Performance) | |
| P1 | Горизонтальное масштабирование интернет-банка и вспомогательных сервисов. | Необходимо для масштабируемости и отказоустойчивости. |
| P2 | АБС масштабируется только вертикально → не использовать его как точку интеграции в реальном времени. | Архитектурное ограничение: все интеграции с АБС должны быть асинхронными или через буфер. |
| P3 | Минимизация нагрузки на систему скоринга (не делать предрасчёты без необходимости). | Требует кэширования скоринговых решений и триггеров только при реальной подаче заявки. |
| S | Поддерживаемость (Supportability) | |
| S1 | Разработка полной технической и пользовательской документации. | Важно для поддержки, но не архитектурно значимо. |
| S2 | Использование технологий, уже известных внутри банка (MS SQL, Oracle, Kafka в перспективе). | Снижает риски и стоимость владения. |
| S3 | Возможность дальнейшего расширения системы (модульность, микросервисный подход). | Особенно важно при возможном переходе интернет-банка на микросервисы. |
| +R | + Ограничения (Restrictions) | |
| DC1 | Нельзя напрямую интегрировать интернет-банк с АБС в реальном времени. | Прямое следствие перегрузки АБС. |
| DC2 | Версия интернет-банка несовместима с Kafka → для MVP использовать альтернативу (например, JMS или REST + буфер). | Ограничение текущей платформы. |
| DC3 | Все новые сервисы должны быть совместимы с существующими платформами разработки. | Упрощает интеграцию и поддержку. |
| I | Реализация (Implementation) | |
| I1 | Реализация логики подачи заявок и управления ставками силами внутренней команды (без привлечения подрядчика к ядру). | Организационное требование. |
| I2 | Внедрение централизованного справочника ставок (в АБС или отдельном сервисе) с доступом для бэк-офиса депозитов и кредитов. | Устраняет зависимость от XLS и упрощает управление. |
| IF2 | Интеграция с Кредитным конвейером, системой скоринга, АБС, ядром (СМС), системой уведомлений. | Требует чёткого контракта и асинхронных паттернов. |
| IF | Интерфейсы (Interface) | |
| IF1 | API для сайта и интернет-банка должны быть унифицированы по структуре и защите. | Упрощает поддержку и масштабирование. |
| PH | Физические (Physical) | |
| PH1 | Хранение персональных данных только в защищённых сегментах сети с шифрованием в покое и в движении. | Соответствие регуляторным требованиям (ФЗ-152, GDPR и др.). |
